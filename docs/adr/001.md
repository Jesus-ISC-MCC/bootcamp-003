# Justificación de decisiones de arquitectura
 
## 1. Strangler Fig Pattern vs. Big Bang Rewrite
 
Para el presente caso práctico se propone utilizar el patrón **Strangler Fig**
como estrategia para la modernización de la solución, en lugar de realizar una
reescritura completa mediante un enfoque **Big Bang Rewrite**.
 
### ¿Qué es Strangler Fig?
 
**Strangler Fig Pattern** es un patrón de modernización que permite sustituir
gradualmente las funcionalidades de un sistema existente por nuevos componentes
o servicios.
 
En lugar de reemplazar toda la aplicación en un solo despliegue, las
funcionalidades se migran progresivamente.
 
El flujo general de la estrategia será:
 
1. El cliente realiza una petición.
2. La petición llega al API Gateway.
3. El Gateway determina si la operación ya fue migrada.
4. Si la funcionalidad pertenece a la nueva arquitectura, la petición se dirige
al nuevo servicio.
5. Si todavía no ha sido migrada, la petición continúa hacia el sistema legado.
6. Este proceso se repite hasta retirar completamente el sistema anterior.

2. ¿Por qué Strangler Fig es mejor que Big Bang Rewrite para este caso?

Un Big Bang Rewrite implicaría desarrollar nuevamente toda la solución y realizar posteriormente un cambio completo del sistema anterior al nuevo.

Para este caso práctico dicho enfoque representa un riesgo mayor, debido a que la migración dependería de que toda la nueva solución estuviera terminada, probada e integrada antes de poder sustituir el sistema existente.

Por el contrario, Strangler Fig permite realizar la modernización de manera incremental, reduciendo el alcance y riesgo de cada liberación.

Comparación
Criterio	Strangler Fig	Big Bang Rewrite
Estrategia de migración	Incremental	Reemplazo completo
Riesgo por liberación	Bajo/Moderado	Alto
Convivencia con sistema legado	Sí	Limitada
Entrega gradual de funcionalidad	Sí	No
Rollback	Por servicio/funcionalidad	Generalmente completo
Validación en producción	Progresiva	Concentrada en el cutover
Tiempo antes de obtener valor	Menor	Mayor
Impacto de una falla	Acotado	Puede afectar toda la migración
Migración por dominio	Sí	Generalmente no
Adaptación ante cambios	Alta	Más costosa
Justificación

Strangler Fig es la estrategia seleccionada porque permite evolucionar la arquitectura sin depender de una migración completa en una sola liberación.

Las funcionalidades pueden extraerse gradualmente del sistema legado y convertirse en nuevos servicios independientes.

Esto proporciona los siguientes beneficios:

Reduce el riesgo operativo, ya que cada componente puede migrarse, validarse y estabilizarse individualmente.
Permite entregas incrementales, evitando esperar a que toda la nueva plataforma se encuentre terminada.
Facilita el rollback, porque una funcionalidad puede mantenerse o regresar temporalmente al sistema legado si el nuevo servicio presenta problemas.
Reduce el impacto de errores, debido a que una falla en un servicio nuevo no necesariamente compromete la migración completa.
Permite pruebas progresivas, tanto funcionales como de integración, rendimiento y seguridad.
Facilita la transición hacia APIs y microservicios, permitiendo extraer capacidades del sistema existente de acuerdo con prioridades técnicas y de negocio.

Por estas razones, Big Bang Rewrite se descarta como estrategia principal, ya que concentra riesgos técnicos, operativos y de integración en una única liberación.

3. Uso de Kong API Gateway
¿Por qué utilizar un API Gateway?

Durante una migración basada en Strangler Fig es necesario contar con un componente capaz de controlar el ingreso de las peticiones y determinar hacia qué implementación deben dirigirse.

Para este caso práctico se utilizará Kong API Gateway como punto central de entrada a las APIs.

                        CLIENTES
                           |
                           v
                 +-------------------+
                 | Kong API Gateway  |
                 +---------+---------+
                           |
             +-------------+-------------+
             |             |             |
             v             v             v
        +---------+   +---------+   +---------+
        | API /   |   | API /   |   | Sistema |
        | Servicio|   | Servicio|   | Legado  |
        |    A    |   |    B    |   |         |
        +---------+   +---------+   +---------+

Kong actuará como una capa desacoplada entre los consumidores y las implementaciones internas de los servicios.

4. Justificación de Kong API Gateway

La selección de Kong API Gateway permite centralizar responsabilidades transversales que no deberían implementarse repetidamente dentro de cada servicio.

Entre ellas se encuentran:

Enrutamiento de peticiones.
Autenticación y autorización.
Rate limiting.
Políticas de seguridad.
Logging.
Monitoreo.
Gestión del tráfico.
Versionamiento y exposición de APIs.
Integración progresiva de nuevos servicios.

Esto es especialmente importante para la implementación del patrón Strangler Fig, ya que Kong puede funcionar como la capa de enrutamiento entre el sistema legado y los nuevos servicios.

Por ejemplo:

/api/v1/clientes  ---> Sistema legado
/api/v2/clientes  ---> Nuevo servicio

/api/v1/pedidos   ---> Sistema legado
/api/v2/pedidos   ---> Nuevo servicio

A medida que una funcionalidad sea migrada, la configuración de routing puede modificarse para dirigir las peticiones hacia la nueva implementación sin que los consumidores necesiten conocer la arquitectura interna.

6. Consideraciones de seguridad

El API Gateway también permite establecer un punto central para aplicar controles de seguridad antes de que las peticiones alcancen los servicios internos.

La arquitectura podrá incorporar controles relacionados con:

Autenticación y autorización.
Rate limiting.
Validación de solicitudes.
Protección y control del tráfico.
Logging y trazabilidad.
Aplicación consistente de políticas de seguridad.
Controles asociados a OWASP API Security Top 10.

La seguridad no dependerá exclusivamente de Kong. Los servicios seguirán aplicando los controles que les correspondan, mientras que el Gateway centralizará aquellas políticas que deben ejecutarse en el perímetro de las APIs.

7. Decisión arquitectónica

Se adopta la combinación:

Strangler Fig Pattern + Kong API Gateway

como estrategia para realizar una modernización incremental de la solución.

Strangler Fig define la estrategia de migración, mientras que Kong API Gateway proporciona el mecanismo de control y enrutamiento necesario para que la arquitectura nueva y la existente puedan coexistir durante la transición.

La decisión busca:

Reducir el riesgo de la migración.
Evitar una sustitución completa tipo Big Bang.
Permitir entregas incrementales.
Mantener temporalmente la compatibilidad con el sistema legado.
Centralizar el acceso a las APIs.
Aplicar políticas de seguridad y control de manera consistente.
Facilitar rollback y resolución de incidentes.
Permitir retirar gradualmente los componentes legados.

Por lo tanto, esta combinación proporciona una estrategia de modernización controlada en la que cada funcionalidad puede ser migrada, probada y liberada de manera independiente antes de retirar definitivamente el sistema anterior.


### Ajuste importante para tu caso práctico

Yo reforzaría especialmente **Kong + Strangler Fig** desde la perspectiva de seguridad. El documento interno [Requisitos de cumplimiento APIs.pdf](https://attmx.sharepoint.com/sites/NormatividadControl/Documentos%20compartidos/Manuales/CSO/Entrega%20de%20infraestructura,%20red%20y%20sistemas/Requisitos%20de%20cumplimiento%20APIs.pdf?web=1&EntityRepresentationId=5394dc1f-6c62-4231-9f59-b5c9a22a9bb4) establece pruebas de **OWASP API Security Top 10 Protection**, **API Behavioral Analytics y detección de Fuzzing** y **OpenAPI Negative Testing**. También indica que para una API interna se debe notificar a Arquitectura de Ciberseguridad el gateway donde será publicada y alcanzar el **100% del cumplimiento de ciberseguridad** para obtener el visto bueno correspondiente. 【1-ec508d】

Esto hace que en tu documento la elección del gateway no quede justificada simplemente porque "Kong es bueno", sino porque **necesitas una capa explícita de gobierno, routing y aplicación de controles mientras conviven el legado y las APIs nuevas**.
